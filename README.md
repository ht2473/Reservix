# Reservix

**Информационная система формирования и развития кадрового резерва организации**

---

## Что это

Система связывает в единый процесс профиль должности, оценку компетенций,
разрывы подготовки и план развития сотрудника. Готовность резервиста к
назначению не назначается экспертным решением, а вычисляется по прозрачной
методике: любое значение раскладывается на составляющие, и видно, что именно
нужно закрыть до назначения.

Отличие от ведения резерва в таблицах — связность данных. Требования к
должности, результаты оценки, выявленные разрывы и мероприятия развития
хранятся не по отдельности, а как единая цепочка.

### Ключевые возможности

| Модуль | Назначение |
|---|---|
| Рабочие места ролей | Стартовая страница каждой роли — очередь того, что требует решения, а не витрина показателей: заявки на согласовании, просроченные пересмотры, планы без подтверждения |
| Кадровый справочник | Карточка сотрудника целиком: место в организации, стаж, оценки, записи резерва, планы развития, положение в матрице, кадровая история, документы |
| Модель компетенций | Справочник компетенций с пятиуровневой шкалой и поведенческими индикаторами; модели привязываются к должностям |
| Оценка персонала | Кампании оценки, круговая оценка 360°, встроенное тестирование, сведение результатов к единой шкале |
| Кадровый резерв | Выдвижение и согласование кандидатов, статусный процесс, группы резерва |
| Индекс готовности | Композитный показатель по шести критериям; веса — экспертные, по методу анализа иерархий или энтропийные; ранжирование взвешенной суммой и методом TOPSIS |
| Матрица 9-box | Автоматическое размещение по осям результативности и потенциала, калибровка руководителями с сохранением истории |
| Преемственность | Критичные должности, списки преемников, глубина скамейки, коэффициент покрытия |
| Планы развития | Мероприятия, привязанные к конкретным разрывам компетенций; вклад видов развития по модели «70—20—10»; выполнение подтверждается документом, а не сменой состояния |
| Наставничество | Пары «наставник — подопечный» со сроком, целью и результатом; ритм встреч, нагрузка и результативность наставника |
| Файловое хранилище | Защищённая выдача документов: обезличенные имена на диске, контрольные суммы, версионирование замещением, доступ по правам на сотрудника |
| Отчётность | Десять отчётов в форматах `.docx`, `.xlsx`, `.pdf` и `.csv`; сборщик данных отделён от писателя формата, один отчёт выгружается в любой формат |
| Уведомления | Лента внутри системы и рассылка по почте; напоминания о сроках мероприятий, просрочке и встречах наставника |
| Публичная часть | Четырнадцать страниц без авторизации: методика, справочник компетенций, калькулятор индекса, обезличенная матрица 9-box, база знаний, глоссарий на 84 термина, справка, нормативные формы |
| Программный интерфейс | REST на django-ninja с описанием OpenAPI; выборки ограничены областью видимости вызывающего |
| Панель администрирования | Девять разделов: учётные записи, оргструктура, справочники, модель скоринга, журнал аудита, данные системы, содержимое портала |

## Технологии

| Слой | Решение | Обоснование |
|---|---|---|
| Язык | Python 3.12.13 | — |
| Пакетный менеджер | uv | Воспроизводимость сборки через `uv.lock` |
| Фреймворк | Django 5.2 LTS | Поддержка до апреля 2028 |
| База данных | PostgreSQL 18 | Полнотекстовый поиск, нечёткое сопоставление имён, оконные функции |
| Кеш, очереди | Redis 7.4, Celery 5.5 | Пересчёт показателей, рассылки, формирование отчётов |
| API | django-ninja | Типизация на Pydantic, автогенерация спецификации OpenAPI |
| Интерфейс | Серверный рендеринг, HTMX 2 | Ощущение одностраничного приложения без его сложности |
| Стили | Собственная дизайн-система | Без препроцессоров и Node в продакшене |
| Аналитика | NumPy, SciPy | Метод анализа иерархий, TOPSIS, энтропийные веса |

**Два языка интерфейса.** Русский и английский; переключатель в шапке, выбор
запоминается в профиле пользователя. Переведены не только подписи разметки, но
и форматы: разделители разрядов, порядок частей даты и правила склонения
счётных слов берутся из действующего языка. Каталоги обслуживает
`scripts/i18n.py` — набор GNU gettext, которого нет в Windows, не требуется.

Справочники и содержимое тоже двуязычные: у переводимых полей есть версии
`_ru` и `_en` (django-modeltranslation). Английские тексты демонстрационных
данных хранятся в `core/translations/en/` и загружаются командой
`load_translations`, которую вызывает `seed_demo`. Системные тексты новых
записей получают английскую версию при сохранении: уведомления и комментарии
переводятся по тем же строкам каталога, что и интерфейс; ФИО транслитерируются.

**Внешних служб нет.** Шрифты, HTMX и библиотека диаграмм размещены локально:
политика безопасности содержимого разрешает загрузку только с собственного
домена, а система должна работать в закрытом контуре без доступа в интернет.

## Быстрый старт

### Требования

* Python 3.12.13 (устанавливается автоматически через `uv`)
* [uv](https://docs.astral.sh/uv/) 0.9 или новее
* Docker с Docker Compose — для PostgreSQL и Redis
* [just](https://github.com/casey/just) — необязательно, упрощает команды

### Установка

```bash
git clone https://github.com/ht2473/Reservix.git
cd Reservix

# Зависимости и виртуальное окружение
uv sync --all-groups

# Конфигурация: скопируйте шаблон и укажите ключ приложения
cp .env.example .env
uv run python -c "import secrets; print(secrets.token_urlsafe(64))"
```

Полученное значение подставьте в переменную `DJANGO_SECRET_KEY` файла `.env`.

```bash
# PostgreSQL, Redis и почтовый сервер-заглушка
docker compose -f deploy/docker-compose.dev.yml up -d

# Схема базы данных
uv run python manage.py migrate

# Наполнение данными: справочники организации, учётные записи, перенос
# исходной базы данных, штат до плановой численности, корпоративная
# модель компетенций, кампании оценки с результатами, текущая работа ролей
uv run python manage.py seed_demo

# Сборка стилей и сценариев
uv run python scripts/build_assets.py

# Сборка каталогов перевода (набор GNU gettext не требуется)
uv run python scripts/i18n.py compile

# Запуск
uv run python manage.py runserver
```

Система доступна по адресу <http://127.0.0.1:8000/>.
Письма, отправленные в режиме разработки, видны на <http://localhost:8025/>.

С установленным `just` последовательность сокращается до одной команды:

```bash
just setup
```

## Исходная база данных

Исходная база `cadr_reserve` включена в репозиторий как есть
(`db/cadr_reserve.sql`) и переносится в модель системы командой:

```bash
uv run python manage.py import_legacy --dry-run   # разбор без записи
uv run python manage.py import_legacy             # перенос
```

Переносятся все 428 строк девяти исходных таблиц без потерь. Свободный текст
приводится к справочникам: наименования целевых должностей и компетенций
сопоставляются со штатным расписанием и справочником компетенций по таблицам
соответствия. Дефекты исходных данных устраняются с выводом отчёта — у 23
карточек не заполнена привязка к подразделению, у 66 выполненных мероприятий
отсутствует дата выполнения. Подробности — в [db/README.md](db/README.md).

### Сведение справочника компетенций

Компетенция в исходной базе существовала строкой в записи об оценке, поэтому
восстановленный из неё справочник содержит 79 наименований — среди них восемь
разновидностей лидерства (`Team Leadership`, `Tech Leadership`,
`Sales Leadership`, `Warehouse Leadership` и далее), шесть вариантов
управления людьми и десять — стратегического мышления.

Последствие не косметическое: руководитель отдела продаж, оценённый по
`sales-leadership`, и руководитель склада, оценённый по
`warehouse-leadership`, не имеют ни одной общей компетенции и потому
несравнимы. Кадровый резерв на управленческую должность из таких данных не
формируется — сравнивать кандидатов не по чему.

Команда `seed_competencies` разворачивает корпоративную модель из 39
компетенций с поведенческими индикаторами по каждому из пяти уровней шкалы и
сводит к ней исходные наименования. Сведение выполняется переносом, а не
удалением: 68 оценок переназначаются на компетенцию-приёмник и продолжают
участвовать в расчётах. Таблица соответствий с обоснованием каждой строки —
в [apps/competencies/dictionary.py](apps/competencies/dictionary.py).

### Как человек попадает в резерв

Запись резерва не создаётся напрямую — ни в интерфейсе, ни через программный
интерфейс. Единственный путь к ней проходит через заявку:

```
заявка с обоснованием
        ↓
согласование руководителем        ← пропускается, если заявку подал он сам
        ↓
решение кадровой службы
        ↓
запись резерва + участие в программе подготовки
```

Ограничение намеренное. Запись, возникшая в обход маршрута, не отвечает на
вопрос «почему этот человек в резерве», а именно его задают через год — при
пересмотре состава и при разборе кадрового решения. Обоснование заявки
переносится в запись и остаётся в ней вместе с историей всех переходов.

Ступень руководителя пропускается ровно в одном случае: заявку подал
непосредственный руководитель кандидата. Спрашивать у человека согласия с его
собственным предложением незачем — ступень существует ради этого согласия, и
подача заявки его уже выражает. Решение при этом фиксируется явно: пустая
ступень в карточке читалась бы как пропуск по ошибке.

### Что закрывает резерв

Список резервистов сам по себе не отвечает на вопрос, обеспечена ли
организация заменой. Ответ даёт связка «критичная должность — план
преемственности — преемники — назначение»:

* критичность должности определяется не уровнем в иерархии, а тем, что
  перестанет работать без этого человека; приоритет планирования — произведение
  критичности на риск освобождения;
* обеспеченность считается по **действующим** планам: должность с отменённым
  планом обеспечена не лучше должности без плана;
* доля назначений из резерва среди всех назначений — главный показатель
  системы. Численность резерва на этот вопрос не отвечает: список может быть
  длинным, а должности при этом закрываться наймом с рынка.

### Как считается индекс готовности

Композитный индекс резервиста (ИГР) складывается из шести частных критериев,
каждый приведён к шкале 0–100: компетентностное соответствие целевой должности,
результативность, потенциал, исполнение плана развития, профессиональный опыт и
сведённая оценка 360°.

**Шкала абсолютная, а не относительная.** Сто баллов означают «требование
выполнено полностью», а не «лучший в группе». Минимаксная нормировка по выборке
отвергнута: при ней индекс кандидата менялся бы от появления в резерве другого
человека, а порог «готов к назначению» терял бы смысл — в слабой группе кто-то
всегда получал бы сто баллов.

**Отсутствие данных — не ноль.** Критерий, для которого исходных данных нет, из
свёртки исключается, а его вес распределяется между остальными. Подстановка
нуля приравняла бы «не оценивали» к «оценили плохо» и наказала бы сотрудника за
незавершённую кадровую процедуру. Вместе с индексом хранится доля веса,
обеспеченная данными, и интерфейс показывает её рядом со значением: индекс 70
при обеспеченности 40 % и такой же индекс при обеспеченности 95 % — разные по
достоверности утверждения.

### Три схемы весов и проверка выводов

Откуда берутся веса критериев — главный методический вопрос, и система не
отвечает на него единственным способом:

| Схема | Как получены веса | Чем ограничена |
|---|---|---|
| Экспертная | Кадровая служба назначает важность в баллах, система нормирует | Прозрачна, но субъективна |
| Метод анализа иерархий | Собственный вектор матрицы парных сравнений по шкале Саати | Субъективность измерима: отношение согласованности выше 0,1 закрывает схему для расчёта |
| Энтропийная | Различающая способность критерия по фактическим данным | Объективна, но игнорирует приоритеты организации |

Свёртка выполняется взвешенной суммой либо методом TOPSIS. Различие
существенно и в интерфейсе не скрывается: взвешенная сумма даёт *абсолютную*
оценку, сравнимую с порогом готовности, TOPSIS — *относительную*, зависящую от
состава сравниваемой группы. Кадровое решение состоит из двух разных вопросов —
«достаточно ли хорош» и «кто лучше из этих», — и подмена одного другим
типичная ошибка систем такого рода.

Наличие трёх схем — не избыточность: выбор способа меняет рейтинг. Система
сравнивает полученные ими ранжирования корреляцией Спирмена и совпадением
состава первой десятки, а также проверяет устойчивость ранжирования к
возмущению весов на 10, 20 и 30 процентов. Ранжирование, разваливающееся при
неточности весов в десятую часть, не может служить основанием кадрового
решения, и знать об этом нужно до того, как решение принято.

### Матрица 9-box и калибровка

Размещение по осям «результативность — потенциал» вычисляется по данным
системы предварительно, а окончательное решение принимает руководитель на
сессии калибровки. Пустая матрица, которую предлагают заполнить с нуля на
четыреста человек, не заполняется никогда; матрица, заполненная только
системой, не показывает главного в процедуре — расхождения между расчётом и
суждением руководителя.

Исходные координаты сохраняются, и расхождение с итогом сессии измеряется
отдельным показателем. Он характеризует не сотрудников, а оценочную культуру
организации: систематический сдвиг вниз означает, что руководители завышают
оценки поодиночке и выравниваются только на общем обсуждении.

Перекос распределения выводится наравне с самим распределением. Если
большинство сотрудников оказалось в одной ячейке, матрица говорит не о
персонале, а о качестве оценки: инструмент, не различающий людей, для отбора
непригоден при любом заполнении.

### Прогноз срока готовности

Срок выхода индекса на порог оценивается линейной экстраполяцией по истории
расчётов. Метод выбран вместо обучаемой модели сознательно: «индекс растёт на
3,2 балла в квартал, до порога осталось 11 баллов, значит около девяти
месяцев» — утверждение, которое можно проверить на бумаге и оспорить.
Вероятность, выданная градиентным бустингом, такой проверке не поддаётся.
Отсутствие прогноза — тоже ответ: «индекс не растёт» отвечает кадровой службе
не хуже даты.

just --list

приведено в [justfile](justfile).

## Архитектурные решения

Ниже — решения, объясняющие устройство системы. Подробности в
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

**Учётная запись отделена от карточки сотрудника.** В исходной базе данных
таблицы `User` и `candidate` дублировали персональные данные, и сотрудник,
одновременно являвшийся пользователем и кандидатом, существовал дважды.
Разделение позволяет заводить сотрудников без доступа в систему, отключать
доступ, сохраняя кадровую историю, и вести внешних кандидатов.

**Права двумерны.** Роль отвечает на вопрос «какие операции разрешены»,
область видимости — «с чьими данными». Два руководителя с одинаковой ролью
могут видеть разный круг сотрудников. Сужение области при понижении роли
выполняется автоматически, расширение — только явным действием администратора.

**Иерархия подразделений хранится материализованным путём.** Структура
организации меняется редко, а читается постоянно — в каждом списке
сотрудников и в каждой проверке прав. Выборка поддерева выполняется одним
сравнением по индексу вместо рекурсивного обхода.

**Цепочка навигации не может быть пустой.** Она формируется конструкцией, а не
дисциплиной разработчика: страница, забывшая объявить крошки, получает
корректную цепочку из одного звена.

**Записи журнала аудита неизменяемы.** Модель запрещает изменение и удаление:
запись, которую можно отредактировать, не является доказательством.

**Дизайн-система написана вручную.** Матрица 9-box — главный аналитический
объект предметной области — служит визуальным лейтмотивом интерфейса:
её сетка, зоны и сигнальная шкала проходят через дашборды, карточки
сотрудников и публичные страницы.

**Сборщик данных отчёта отделён от писателя формата.** Между ними стоит
нейтральное описание отчёта: заголовок, реквизиты, показатели и таблицы с
типизированными столбцами. Сборщик знает о резервистах и не знает о форматах;
писатель знает об абзацах и ячейках и не знает о предметной области. Следствий
три: один отчёт выгружается в любой из четырёх форматов без дополнительного
кода, сборщик проверяется тестом по составу строк вместо разбора двоичного
файла, а новый формат добавляется одной функцией.

**Числа в таблице Excel остаются числами.** В `.docx`, `.pdf` и `.csv` значение
попадает строкой, оформленной по русскому образцу; в `.xlsx` — числом с
числовым форматом ячейки. Различие принципиально: записанное строкой число не
суммируется и не сортируется, и выгрузка перестаёт быть рабочим материалом.

**План развития строится от разрывов, а не от каталога курсов.** Каждое
мероприятие привязано к требованию модели компетенций, недобор по которому оно
закрывает, и вклад мероприятия в выполнение плана зависит от вида развития по
модели «70—20—10». К моменту завершения плана видно не «пройдено пять курсов»,
а по каким компетенциям разрыв закрыт.

**Мероприятие закрывается документом, а не кнопкой.** Для обучения, курса и
конференции требуется подтверждение — сертификат, отчёт, отзыв наставника;
проверяет его не тот, кто приложил. Требование снижает долю выполненных
планов, и это плата за то, что оставшаяся доля означает нечто проверяемое.

**Файл документа не имеет прямого адреса.** Имя на диске обезличено, каталог
закрыт настройками веб-сервера, выдача идёт через представление с проверкой
права доступа. Право на документ выводится из права на сотрудника, которого он
касается: собственный уровень доступа документа способен только сузить круг
читателей, но не расширить его.

**Публичные показатели обезличены по построению.** Страницы открыты поисковым
обходчикам, поэтому наружу выходят численности и доли, но не сведения о людях.
При этом распределение по матрице 9-box берётся из системы, а не задаётся
числами в разметке: придуманное распределение всегда выглядит благополучным, а
настоящее показывает перекос, если он есть.

## Тестирование

```bash
just test            # быстрый прогон: модульные и интеграционные
just test-cov        # с отчётом о покрытии
just test-security   # проверки по классификации OWASP Top-10
just browsers        # установить браузеры для сквозных сценариев
just test-e2e        # сквозные сценарии в браузере
just load-test       # нагрузочное тестирование
```

Проверки разложены по каталогам `tests/`:

| Каталог | Что проверяет |
|---|---|
| `unit` | расчётное ядро, сервисы, формы, навигация, перевод данных |
| `integration` | страницы и процессы под каждой ролью на PostgreSQL |
| `e2e` | сквозные сценарии и адаптивность в браузере (Playwright) |
| `security` | проверки по классификации OWASP Top-10 |
| `load` | профили нагрузки по ролям для Locust |

Сквозные сценарии пропускаются с явной причиной, если браузер не установлен:
молчаливо проходящая проверка хуже отсутствующей.

## Развёртывание

Развёртывание на сервере описано в [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).
Установка на чистый сервер выполняется одной командой:

```bash
sudo ./deploy/install.sh reservix.ru admin@reservix.ru
```

Скрипт ставит Docker, готовит каталоги, генерирует секреты, настраивает
межсетевой экран, выпускает сертификат, поднимает службы и включает
ежедневное резервное копирование. Он идемпотентен: повторный запуск не ломает
работающую установку, а доводит недостающее — первый запуск на чужом сервере
почти всегда обрывается на середине.

Обслуживание:

```bash
./deploy/update.sh              # обновление с автоматическим откатом при отказе
./deploy/backup.sh --verify     # копия с проверкой восстановлением
./deploy/restore.sh --list      # перечень копий
./deploy/renew-cert.sh --status # сроки действия сертификатов
```

Без установщика, вручную:

```bash
cd deploy
docker compose --env-file ../.env up -d --build
```

Поднимаются nginx с завершением TLS, приложение под gunicorn, PostgreSQL,
Redis, воркер фоновых задач и планировщик расписаний. Наружу открыт только
nginx: база данных и Redis доступны исключительно внутри сети контейнеров.

**Шрифт для выгрузки в PDF.** Библиотека `reportlab` располагает только
латинскими встроенными начертаниями, поэтому образ приложения устанавливает
`fonts-dejavu-core`. Путь к шрифту можно задать переменной `PDF_FONT_PATH`;
при отсутствии пригодного шрифта выгрузка в PDF отключается с явным
сообщением, а остальные три формата продолжают работать.

**Периодические задачи** регистрируются планировщиком в базе данных
(`django_celery_beat`) и выполняются воркером:

| Задача | Назначение | Ритм |
|---|---|---|
| `apps.development.tasks.mark_overdue_activities` | Признак просрочки мероприятий | раз в сутки |
| `apps.development.tasks.notify_due_soon` | Напоминание исполнителю о сроке | раз в сутки |
| `apps.development.tasks.notify_overdue` | Извещение куратора о просрочке | раз в неделю |
| `apps.development.tasks.remind_mentorship_meetings` | Напоминание наставнику о встрече | раз в неделю |
| `apps.development.tasks.notify_expiring_plans` | Извещение об истекающем плане | раз в неделю |
| `apps.notifications.tasks.send_pending_emails` | Рассылка накопленных писем | каждые 10 минут |
| `apps.reporting.tasks.cleanup_reports` | Удаление выгрузок старше 90 дней | раз в сутки |
