# Развёртывание

Документ описывает установку системы на сервер, её обслуживание и
восстановление. Изложение рассчитано на человека, который разворачивает
систему впервые и не знаком с её устройством.

---

## 1. Требования к серверу

| Ресурс | Минимум | Рекомендуется | Почему |
|---|---|---|---|
| Процессор | 2 ядра | 4 ядра | пересчёт индексов по организации и формирование отчётов идут в фоне и конкурируют с веб-запросами |
| Память | 2 ГБ | 4 ГБ | PostgreSQL 256 МБ разделяемых буферов, Redis 256 МБ, два процесса Python |
| Диск | 20 ГБ | 40 ГБ | база растёт медленно, место занимают документы и резервные копии за месяц |
| ОС | Ubuntu 24.04 LTS | Ubuntu 24.04 LTS | проверено; Debian 12 работает так же |

Наружу открываются порты 22, 80 и 443. Порты PostgreSQL и Redis не
открываются никогда: службы доступны только внутри сети контейнеров.

**Бесплатная площадка.** Oracle Cloud Always Free даёт постоянно бесплатную
виртуальную машину ARM (4 vCPU, 24 ГБ), на которую тот же `docker compose`
ставится без изменений. Запасные варианты — Render Free (засыпает после
15 минут простоя) и PythonAnywhere Free (нет PostgreSQL, потребуется профиль
настроек с SQLite).

## 2. Установка

### 2.1. Одной командой

```bash
git clone https://github.com/ht2473/Reservix.git /opt/reservix
cd /opt/reservix
sudo ./deploy/install.sh reservix.ru admin@reservix.ru
```

Скрипт доводит чистый сервер до работающей системы: ставит Docker, создаёт
системного пользователя и каталоги, генерирует секреты, настраивает межсетевой
экран, выпускает сертификат, собирает образ, поднимает контейнеры, настраивает
резервное копирование и ротацию журналов.

**Скрипт идемпотентен.** Повторный запуск не ломает работающую установку, а
доводит недостающее. Это не удобство, а требование к установщику: первый
запуск на чужом сервере почти всегда обрывается на середине — не разрешилось
имя домена, не открылся порт, не хватило места.

### 2.2. Что делает установщик

| Шаг | Действие | Проверить, если не сработало |
|---|---|---|
| 1 | Системные пакеты, включая `fonts-dejavu-core` | `fc-list \| grep -i dejavu` |
| 2 | Docker Engine и плагин compose | `docker --version` |
| 3 | Пользователь `reservix`, каталоги `/opt/reservix`, `/var/backups/reservix`, `/var/log/reservix` | `id reservix` |
| 4 | Исходный код | `git -C /opt/reservix log -1` |
| 5 | `.env` с сгенерированными секретами | `sudo cat /opt/reservix/.env` |
| 6 | Правила `ufw`: 22, 80, 443 | `sudo ufw status` |
| 7 | Сертификат Let's Encrypt | `./deploy/renew-cert.sh --status` |
| 8 | Сборка образа и запуск служб | `docker compose ps` |
| 9 | Администратор системы | сообщение установщика |
| 10 | Ежедневное резервное копирование в 03:30 | `cat /etc/cron.d/reservix-backup` |
| 11 | Ротация журналов | `cat /etc/logrotate.d/reservix` |

Шрифт с поддержкой кириллицы (шаг 1) — не косметика: `reportlab` не поставляет
таких начертаний, и без системного шрифта выгрузка отчётов в PDF отключается.
Остальные три формата при этом работают, а на странице каталога отчётов
выводится объяснение.

### 2.3. После установки

```bash
cd /opt/reservix/deploy

# Администратор системы
docker compose exec web python manage.py createsuperuser

# Демонстрационные данные — только на стенде, не в рабочей системе
docker compose exec web python manage.py seed_demo
```

## 3. Состав служб

| Служба | Образ | Назначение | Открыт наружу |
|---|---|---|---|
| `nginx` | nginx:1.29-alpine | TLS, статика, ограничение частоты запросов, `X-Accel-Redirect` | 80, 443 |
| `web` | reservix:latest | Django под gunicorn | нет |
| `worker` | reservix:latest | Celery: очереди `default`, `analytics`, `reports`, `notifications` | нет |
| `beat` | reservix:latest | планировщик периодических задач | нет |
| `postgres` | postgres:18-alpine | база данных | нет |
| `redis` | redis:7.4-alpine | кеш, брокер, сессии | нет |
| `certbot` | certbot/certbot | выпуск и продление сертификата | нет |

Разделение сетей: `frontend` — nginx и приложение, `backend` — приложение,
база и Redis. Даже при ошибке в правилах межсетевого экрана порт PostgreSQL
не окажется открытым в интернет.

**Миграции и сбор статики выполняются командой запуска контейнера `web`.**
Развёртывание сводится к одной команде, а состояние базы всегда соответствует
коду образа. Отдельного шага «применить миграции» нет ни при установке, ни
при обновлении — и потому его невозможно забыть.

## 4. Настройка

Все различающиеся между установками значения берутся из `.env`. Файл создаётся
установщиком с правами `600` и владельцем `reservix`.

### 4.1. Обязательные значения

| Переменная | Назначение |
|---|---|
| `DJANGO_SECRET_KEY` | ключ подписи сессий и токенов; генерируется установщиком |
| `DJANGO_ALLOWED_HOSTS` | домены, с которых принимаются запросы |
| `CSRF_TRUSTED_ORIGINS` | источники, которым доверяется защита от подделки запросов |
| `POSTGRES_PASSWORD` | пароль базы; генерируется установщиком |

**Секретный ключ уникален для установки.** Общий ключ на нескольких
установках означает, что сессия одной подходит к другой, а токен сброса
пароля, выданный на стенде, работает в рабочей системе.

### 4.2. Почта

Без настроенной почты не уходят уведомления о сроках, приглашения на оценку
и восстановление пароля. Установщик об этом предупреждает.

```bash
EMAIL_HOST=smtp.yandex.ru
EMAIL_PORT=587
EMAIL_HOST_USER=reservix@example.ru
EMAIL_HOST_PASSWORD=пароль-приложения
EMAIL_USE_TLS=True
DEFAULT_FROM_EMAIL=Reservix <reservix@example.ru>
```

Проверка:

```bash
docker compose exec web python manage.py sendtestemail admin@example.ru
```

### 4.3. Производительность

| Переменная | По умолчанию | Когда менять |
|---|---:|---|
| `GUNICORN_WORKERS` | 3 | при 4 ядрах — 5; формула `2 × ядра + 1` |
| `GUNICORN_THREADS` | 2 | увеличивать при медленной базе, а не при медленном коде |
| `CELERY_CONCURRENCY` | 2 | при отдельном воркере на очередь `analytics` — 1 |
| `REDIS_MAXMEMORY` | 256mb | при кешировании отчётов — 512mb |
| `DB_CONN_MAX_AGE` | 60 | 0 при работе через внешний пул соединений |

## 5. Обслуживание

### 5.1. Обновление

```bash
/opt/reservix/deploy/update.sh              # до последнего коммита
/opt/reservix/deploy/update.sh v1.2.0       # до указанной метки
/opt/reservix/deploy/update.sh --rollback   # возврат на предыдущий образ
```

Порядок шагов продиктован одним требованием: **в любой момент обновления
должен существовать способ вернуться назад**. Отсюда резервная копия до
первого изменения, сборка образа до остановки старого, сохранение прежнего
образа под меткой `reservix:previous` и автоматический откат, если приложение
не поднялось за две минуты.

Откат возвращает образ, но **не откатывает миграции базы**. Если новая версия
меняла схему, возврат выполняется восстановлением из копии, снятой скриптом
перед обновлением.

### 5.2. Резервное копирование

Выполняется ежедневно в 03:30. Копируются три вещи, и все три обязательны:

* **база** — дамп `pg_dump` в собственном формате (сжатый, допускает
  выборочное восстановление отдельных таблиц);
* **медиафайлы** — загруженные документы и фотографии; дамп без них
  восстанавливает систему со ссылками в никуда;
* **`.env`** — без него дамп бесполезен: секретный ключ входит в хеши токенов
  сброса пароля, а пароль базы нужен для подключения.

```bash
/opt/reservix/deploy/backup.sh              # обычный запуск
/opt/reservix/deploy/backup.sh --verify     # с проверкой восстановлением
```

**Копия проверяется сразу после создания.** Резервная копия, которую ни разу
не читали, — не копия, а надежда: повреждённый архив обнаруживается в момент
восстановления, то есть в худший из возможных моментов. Обычный запуск
читает оглавление дампа; `--verify` разворачивает его во временную базу и
считает записи.

Шифрование `.env` включается переменной `BACKUP_PASSPHRASE`. Без неё файл
сохраняется открытым текстом, и скрипт об этом сообщает.

Срок хранения — 30 дней (`RETENTION_DAYS`).

### 5.3. Восстановление

```bash
/opt/reservix/deploy/restore.sh --list                    # перечень копий
/opt/reservix/deploy/restore.sh /var/backups/reservix/db-20260830-033000.dump
```

Порядок: сверка контрольных сумм → проверка читаемости дампа → подтверждение
вводом слова `ВОССТАНОВИТЬ` → **копия текущего состояния** → остановка
приложения → восстановление базы → восстановление медиафайлов → запуск →
сверка контрольных сумм документов.

Копия текущего состояния снимается всегда, даже когда «восстанавливаем поверх
мусора»: ошибка в выборе файла обнаруживается уже после того, как прежние
данные стёрты.

Последний шаг — сверка документов — существен именно после восстановления:
база и медиафайлы копируются раздельно и могут оказаться из разных копий.
Расхождение проявилось бы при первом открытии карточки, то есть через неделю,
когда связь с восстановлением уже не очевидна.

### 5.4. Сертификат

Продлевается автоматически контейнером `certbot` (проверка каждые 12 часов).
Ручное управление:

```bash
./deploy/renew-cert.sh --status     # сроки действующих сертификатов
./deploy/renew-cert.sh --dry-run    # проверка процедуры без обращения к УЦ
./deploy/renew-cert.sh              # продлить, если срок близок
./deploy/renew-cert.sh --force      # продлить принудительно
```

После продления скрипт заставляет nginx перечитать конфигурацию. Пропуск этого
шага — самая частая причина жалобы «сертификат продлён, а браузер ругается на
просроченный»: nginx держит открытым тот файл, который прочитал при старте.

Пробный прогон обращается к тестовому серверу Let's Encrypt: боевой ограничен
по частоте, и пять неудачных попыток в час блокируют домен на неделю.

### 5.5. Журналы

```bash
docker compose logs -f web            # приложение
docker compose logs -f worker         # фоновые задачи
tail -f /var/log/reservix/backup.log  # резервное копирование
journalctl -u reservix-backup         # если используется таймер systemd
```

Ротация: ежедневно, хранение 30 дней; журнал резервного копирования —
еженедельно, хранение полугода. Срок разбора инцидента в кадровой системе
измеряется днями: жалоба на неверный расчёт индекса доходит до администратора
через неделю после самого расчёта.

### 5.6. Проверка состояния

```bash
curl -s https://reservix.ru/health/ | jq
```

```json
{"status": "ok", "checks": {"database": "ok", "cache": "ok"}}
```

Ответ `503` со `status: unavailable` означает недоступность базы или кеша.
Адрес вынесен за языковые префиксы: его опрашивает контейнерное окружение, и
язык интерфейса на состав ответа не влияет.

## 6. Управление через systemd

Docker Compose перезапускает упавшие контейнеры сам. Юнит systemd решает
другую задачу — **порядок при загрузке сервера**: без него compose стартует
одновременно с сетью и файловыми системами, и запуск на холодном сервере
оказывается гонкой, которая иногда проигрывается.

```bash
sudo cp deploy/systemd/reservix.service /etc/systemd/system/
sudo cp deploy/systemd/reservix-backup.* /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now reservix
sudo systemctl enable --now reservix-backup.timer
```

Таймер systemd предпочтительнее записи в cron для резервного копирования:
он переживает пропущенный запуск (сервер был выключен в 03:30) и выполняет
задание при следующей загрузке, тогда как cron такой запуск теряет. Именно
пропущенные копии обнаруживаются последними.

## 7. Разбор неисправностей

| Признак | Вероятная причина | Что проверить |
|---|---|---|
| `502 Bad Gateway` | приложение не поднялось | `docker compose logs web` — обычно ошибка миграции или неверный `DATABASE_URL` |
| Страница без оформления | статика не собрана | `docker compose exec web python manage.py collectstatic --noinput` |
| Не уходят письма | не настроен SMTP | `docker compose exec web python manage.py sendtestemail …` |
| Выгрузка в PDF недоступна | нет шрифта с кириллицей | `docker compose exec web fc-list \| grep -i dejavu` |
| Медленные страницы | не хватает воркеров | `GUNICORN_WORKERS`, затем нагрузочный прогон (§ 8) |
| Не продлевается сертификат | домен не указывает на сервер | `./deploy/renew-cert.sh --dry-run` |
| Документ не открывается | файл повреждён или из другой копии | `docker compose exec web python manage.py verify_documents` |
| Браузер ругается на просроченный сертификат | nginx не перечитал конфигурацию | `docker compose exec nginx nginx -s reload` |

## 8. Проверка под нагрузкой

```bash
# На стенде с демонстрационными данными
LOAD_HR_EMAIL=hr@reservix.local \
LOAD_MANAGER_EMAIL=manager@reservix.local \
LOAD_PASSWORD='…' \
uv run locust -f tests/load/locustfile.py --host https://reservix.ru \
    --headless --html reports/load.html
```

Профиль ступенчатый: 50 → 200 → 500 пользователей с удержанием на каждой
ступени и спадом в конце. Ступени, а не плавный рост: цель — увидеть, как
меняется время ответа при удержании нагрузки, а не найти точку отказа. Спад в
конце показывает, восстанавливается ли система — именно это отличает нехватку
ресурсов от утечки.

Прогон завершается с ненулевым кодом, если доля отказов превышает 1 %, 95-й
процентиль времени ответа — 1500 мс либо медиана — 500 мс.

**Нагрузку снимают на копии, а не на рабочей системе.**

## 9. Перенос на другой сервер

```bash
# На старом сервере
/opt/reservix/deploy/backup.sh
scp /var/backups/reservix/db-*.dump /var/backups/reservix/media-*.tar.gz новый:/var/backups/reservix/

# На новом сервере
sudo ./deploy/install.sh reservix.ru admin@reservix.ru
/opt/reservix/deploy/restore.sh /var/backups/reservix/db-….dump
```

Файл `.env` переносится отдельно и целиком: заново сгенерированный секретный
ключ сделает недействительными все сессии и токены сброса пароля.
