# Программный интерфейс

REST-интерфейс системы построен на django-ninja: маршруты описываются
типизированными функциями, а описание OpenAPI формируется из тех же
аннотаций, что и проверка данных. Расхождение между документацией и
поведением поэтому невозможно — документация не пишется отдельно.

**Адрес:** `/api/v1/`
**Интерактивная документация:** `/api/v1/docs`
**Описание OpenAPI:** `/api/v1/openapi.json`

## Аутентификация

Поддерживаются два способа.

**Сеанс веб-интерфейса** — для запросов из самой системы. Пользователь уже
вошёл, и предъявлять учётные данные повторно не требуется.

**Базовая аутентификация HTTP** — для внешних потребителей: кадровой
отчётности, выгрузок в систему документооборота, сценариев сопровождения.

```bash
curl -u hr@meridian-soft.ru:пароль https://reservix.example.com/api/v1/system/me
```

Токены доступа не предусмотрены намеренно. Токен — это сущность со сроком
действия, отзывом и хранением; вводить её ради двух внешних потребителей
означало бы усложнить систему без выигрыша. Базовая аутентификация применяется
поверх обязательного TLS, а защиту от подбора обеспечивает тот же механизм,
что и для формы входа: учёт неудачных попыток и блокировка.

## Область видимости

Каждый метод возвращает данные в границах прав вызывающего. Ограничение
накладывается на уровне набора запросов, а не проверкой после выборки: иначе
постраничная навигация показывала бы разное число записей на страницах, а
счётчик результатов раскрывал бы численность недоступных подразделений.

| Роль | Что видит |
|---|---|
| Администратор, HR-специалист | Всю организацию |
| Руководитель | Своё подразделение и все вложенные |
| Наставник, сотрудник | Собственные данные |

Отсутствие записи в ответе не означает, что её нет в системе. Обращение к
недоступной записи по прямому адресу возвращает `403`, а для сессий оценки —
`404`: ответ «нет прав» сам по себе подтверждал бы существование оценки
конкретного сотрудника.

## Формат ошибок

Все отказы имеют одинаковую структуру: машиночитаемый код, пояснение для
человека и, при ошибке разбора запроса, разбор по полям.

```json
{
  "code": "validation_error",
  "detail": "Запрос содержит недопустимые значения",
  "fields": {
    "justification": ["String should have at least 30 characters"]
  }
}
```

| Код HTTP | `code` | Когда возникает |
|---|---|---|
| 400 | `invalid_transition`, `duplicate_nomination`, `not_eligible`, `invalid_data` | Нарушено правило предметной области |
| 401 | `unauthorized` | Учётные данные не предъявлены либо неверны |
| 403 | `forbidden` | Пользователь опознан, но операция ему недоступна |
| 404 | `not_found` | Запись не найдена либо недоступна вызывающему |
| 422 | `validation_error` | Запрос не прошёл проверку типов и ограничений |
| 500 | `internal_error` | Непредвиденная ошибка; подробности — только в журнале |

Текст непредвиденной ошибки наружу не выдаётся: он способен раскрыть структуру
базы данных и пути файловой системы.

## Постраничная навигация

Списочные методы принимают `limit` и `offset` и возвращают объект с полями
`items` и `count`:

```json
{ "items": [ … ], "count": 442 }
```

Предельное значение `limit` ограничено настройкой `NINJA_PAGINATION_MAX_LIMIT`
(200): без ограничения один запрос мог бы выгрузить кадровые данные всей
организации и исчерпать память рабочего процесса.

### Компетенции

| Метод | Адрес | Назначение |
|---|---|---|
| GET | `/competencies/categories` | Категории справочника |
| GET | `/competencies/competencies` | Компетенции с определениями |

| GET | `/competencies/profiles/{employee_id}` | Профиль соответствия сотрудника должности |

**Профиль соответствия** — главное, ради чего внешней системе может
понадобиться этот раздел. Метод отвечает на вопрос «насколько сотрудник
соответствует требованиям должности» одним числом и расшифровкой по
компетенциям::

    GET /api/v1/competencies/profiles/3ffb302d-287e-476e-b9b6-6c3a3228b537

```json
{
  "employee_id": "3ffb302d-287e-476e-b9b6-6c3a3228b537",
  "competency_model_name": "Продажи",
  "match_score": 88.8,
  "coverage": 100.0,
  "confidence": 0.203,
  "is_blocked": false,
  "gaps": [
    {
      "competency_name": "Технология продаж",
      "target_level": 4,
      "actual_level": 3.5,
      "gap": 0.5,
      "weight": "0.240",
      "attainment": 0.833,
      "is_critical": true,
      "is_satisfied": false,
      "is_blocking": true,
      "confidence": 0.203,
      "methods": 1
    }
  ]
}
```

Три поля ответа заслуживают пояснения, поскольку без них показатель
соответствия истолковывается неверно.

* `coverage` — доля требований, подтверждённых хотя бы одной оценкой.
  Соответствие 40 % при покрытии 30 % означает не слабого кандидата, а
  незавершённую оценку. Потребитель обязан различать эти случаи: неоценённая
  компетенция считается неподтверждённой, а не нулевой.
* `confidence` — доля веса методов оценки, фактически применённых. Уровень
  4,0, полученный из одной самооценки, и такой же уровень, подтверждённый
  тестом и руководителем, — разные утверждения.
* `is_blocking` — недобор по критичному требованию. Он закрывает путь к
  назначению независимо от итогового процента: компетенции не
  взаимозаменяемы, и превышение по одной не компенсирует провал по другой.

Параметр `model` сопоставляет сотрудника с требованиями другой должности —
так оценивается готовность к назначению::

    GET /api/v1/competencies/profiles/{employee_id}?model=tier-head

Выборка ограничена областью видимости так же, как выборка сотрудников.
Сотрудник вне области видимости и несуществующий сотрудник дают одинаковый
ответ `404`: ответ «нет прав» сам по себе подтверждал бы, что такой сотрудник
существует.

### Кадровый резерв

| Метод | Адрес | Назначение |
|---|---|---|
| GET | `/reserve/groups` | Группы подготовки резерва |
| GET | `/reserve/entries` | Состав резерва |
| GET | `/reserve/entries/{public_id}` | Запись резерва |
| GET | `/reserve/entries/{public_id}/history` | История смены статусов |
| POST | `/reserve/entries/{public_id}/transition` | Смена статуса записи |
| GET | `/reserve/nominations` | Заявки на выдвижение |
| POST | `/reserve/nominations` | Подача заявки |
| POST | `/reserve/nominations/{public_id}/decision` | Решение согласующего |

Смена статуса проходит те же проверки, что и в веб-интерфейсе: таблицу
допустимых переходов и права роли. Программный интерфейс не является обходным
путём мимо процедуры — восстановить исключённого резервиста, минуя новое
выдвижение, нельзя ни через форму, ни через запрос.

```bash
curl -X POST -u hr@meridian-soft.ru:пароль \
  -H "Content-Type: application/json" \
  -d '{"status": "active", "reason": "Оценка подтвердила готовность"}' \
  https://reservix.example.com/api/v1/reserve/entries/<public_id>/transition
```

**Решение по заявке.** Ступень маршрута в запросе не указывается: она
определяется состоянием заявки. Иначе согласующий закрывал бы обе ступени —
руководителя и кадровой службы — одним вызовом, и двухступенчатый маршрут
перестал бы существовать. Одобрение на ступени кадровой службы создаёт запись
резерва в той же операции: состояния «заявка одобрена, записи нет» не бывает.

```bash
curl -X POST -u hr@meridian-soft.ru:пароль \
  -H "Content-Type: application/json" \
  -d '{"approve": true, "comment": "Зачислен в резерв", "reserve_group_id": 1}' \
  https://reservix.example.com/api/v1/reserve/nominations/<public_id>/decision
```

### Преемственность

| Метод | Адрес | Назначение |
|---|---|---|
| GET | `/succession/key-positions` | Критичные должности с приоритетом планирования |
| GET | `/succession/plans` | Планы преемственности со списками преемников |
| GET | `/succession/plans/{public_id}` | План преемственности |
| GET | `/succession/appointments` | Назначения |
| GET | `/succession/coverage` | Обеспеченность критичных должностей |
| GET | `/succession/statistics` | Результативность: доля назначений из резерва |

**Об отборе незакрытых должностей.** Параметр `uncovered` метода
`/succession/key-positions` оставляет должности без **действующего** плана, а
не без плана вообще. Различие не формальное: должность, план по которой закрыт
или отменён, обеспечена не лучше должности без плана, и выпадать из рабочего
списка кадровой службы она не должна.

**О трёх показателях обеспеченности.** Метод `/succession/coverage` возвращает
покрытие, глубину скамейки и немедленную готовность раздельно: они отвечают на
разные вопросы — где вообще нет преемников; хватит ли запаса при отказе первого
кандидата; что произойдёт, если уход случится завтра. Организация с полным
покрытием и нулевой немедленной готовностью выглядит благополучно ровно до
первого заявления об увольнении.

```bash
curl -u hr@meridian-soft.ru:пароль \
  https://reservix.example.com/api/v1/succession/statistics?year=2026
```

**Расчёт и чтение разделены.** Методы `snapshots`, `nine-box` и `metrics`
читают сохранённые результаты: пересчёт индекса по нескольким сотням
резервистов занимает секунды, и выполнять его в обработчике запроса значит
поставить отзывчивость в зависимость от объёма организации. Исключение —
`breakdown`, `comparison` и `stability`: они по определению возвращают то, чего
в базе нет. Объём выборки в двух последних ограничен параметром `limit`, а
фактически использованный объём возвращается в самом ответе.

#### Разбор индекса готовности

`/analytics/breakdown/{entry_id}` возвращает не значение, а его составляющие.
Индекс без разбора — число, которое нечем объяснить резервисту, а именно
объяснение определяет содержание плана развития.

Поле `coverage` — доля веса критериев, для которых нашлись исходные данные.
Критерий без данных из свёртки исключается, а его вес распределяется между
остальными: подстановка нуля приравняла бы «не оценивали» к «оценили плохо».
Индекс 70 при `coverage` 0,4 и такой же индекс при `coverage` 0,95 — разные по
достоверности утверждения, и различать их обязан потребитель, а не догадка.

```json
{
  "entry_id": 69,
  "scheme": "expert-baseline",
  "aggregation": "weighted_sum",
  "index_value": 86.71,
  "readiness_level": "high",
  "coverage": 0.75,
  "is_reliable": true,
  "rank": 1,
  "candidates_total": 1,
  "contributions": [
    {
      "code": "k1-competency",
      "name": "Компетентностное соответствие",
      "value": 99.3,
      "weight": 0.4,
      "points": 39.72,
      "has_data": true,
      "note": "Оценкой покрыто 100 % требований"
    },
    {
      "code": "k4-development",
      "name": "Исполнение плана развития",
      "value": 0.0,
      "weight": 0.0,
      "points": 0.0,
      "has_data": false,
      "note": "План развития не составлен либо срок мероприятий не наступил"
    }
  ]
}
```

#### Сравнение схем и устойчивость

`/analytics/comparison` отвечает на вопрос, меняет ли выбор методики кадровое
решение. Рядом с корреляцией Спирмена приводится `top_agreement` — совпадение
состава головной части списка. Показатель не дублирует корреляцию: значение
0,9 при полностью разной первой десятке достижимо согласием в хвосте списка,
который на решения не влияет.

```json
{
  "entries": 79,
  "top_size": 10,
  "verdict": "Ранжирования согласованы: выбор схемы почти не влияет на порядок",
  "min_correlation": 0.9662,
  "pairs": [
    {
      "left": "expert-baseline",
      "right": "ahp-hierarchy",
      "correlation": 0.997,
      "top_agreement": 1.0
    }
  ]
}
```

`/analytics/stability` возмущает вес каждого критерия на 10, 20 и 30 процентов
в обе стороны и пересчитывает ранжирование. Поля `entries` и `entries_total`
приводятся вместе: заключение «ранжирование устойчиво», полученное на трети
выборки, вводит в заблуждение, а по одному значению корреляции отличить эти
случаи невозможно.

```json
{
  "scheme": "expert-baseline",
  "entries": 75,
  "entries_total": 79,
  "criteria": 4,
  "worst_correlation": 0.9737,
  "average_stability": 0.5161,
  "is_robust": true,
  "critical_criterion": "k1-competency",
  "by_criterion": [
    {
      "code": "k1-competency",
      "name": "Компетентностное соответствие",
      "worst_correlation": 0.9737,
      "worst_delta": -0.3,
      "stable_share": 0.36,
      "max_rank_shift": 8.0
    }
  ]
}
```

#### Прогноз готовности

`/analytics/forecast/{entry_id}` оценивает срок выхода индекса на порог
готовности линейной экстраполяцией по истории расчётов. Метод выбран вместо
обучаемой модели сознательно: прогноз обязан быть объяснимым резервисту и
проверяемым на бумаге. Отсутствие прогноза возвращается содержательным ответом
в поле `note` («индекс не растёт», «нужно не менее трёх расчётов»), а не
ошибкой: это тоже вывод.

## Ограничение частоты запросов

Настройка `NINJA_DEFAULT_THROTTLE_RATES` ограничивает неаутентифицированные
запросы шестьюдесятью в минуту, аутентифицированные — шестьюстами. Ограничение
защищает не столько от нагрузки, сколько от последовательного перебора: без
него доступный сотруднику метод сведений о себе позволил бы установить
численность организации по времени ответа.

## Проверка

Интерфейс покрыт интеграционными тестами (`tests/integration/test_api.py` и
